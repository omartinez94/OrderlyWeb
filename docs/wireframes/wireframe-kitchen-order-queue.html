Design rationale — numbered annotations

Cross-ref research/competitive-analysis-restaurant-crm.md §5.2 + website-spec.md §5.4 & §6.5
  1. 1

    Connection status chip — always visible, top-left

    website-spec.md §5.4 mandates a connection status indicator. Placed prominently in the top bar because if SignalR drops, the KDS is *useless* (tickets won't arrive). The pulse animation on the green dot is a subtle "I'm alive" signal — no fancy toast pop-ups. Latency readout (12 ms) helps when troubleshooting. Shows the actual hub path (/hubs/orders) per website-spec.md §7.3.

  2. 2

    Time indicator — top of card, big monospace

    Implements website-spec.md §6.5 KDS time-color logic exactly: green <80%, yellow 80–100%, red >100%. The elapsed time and % are at the top of the card — chefs' eyes scan top-down (pattern from Toast KDS, Fresh KDS, Lightspeed KDS). Monospace 36px keeps width predictable across different elapsed times; jumping widths would make scanning harder.

  3. 3

    BUMP primary CTA — 56pt tap target

    Bump is the single most-used KDS action. 14px h-14 button = 56pt tap target (Apple HIG minimum is 44pt; we exceed). Bordered + filled tint so it reads at distance, color tracks the time indicator for at-a-glance scan. Bump signals "ready, send it to expo / runner". The "swipe →" hint is a power-user gesture available in the eventual implementation, but the button is the canonical path.

  4. 4

    Card grid — 4 columns desktop, no scroll inside a card

    Common KDS pattern across Toast / Square / TouchBistro / Lightspeed / Fresh KDS: tickets live in a CSS grid; chefs scan the whole board, not pages. The grid responds — 5 columns at 1920 px, 4 at 1440 px (this view), 3 at 1024 px, 2 at tablet-portrait. No horizontal scroll, no pagination. Every ticket must fit in one card face without internal scrolling (lifted from TouchBistro KDS best practice).

  5. 5

    Order type + items body — compact, monospace quantities

    Top of body shows order type (Dine-in / Takeout / Delivery / Bar) per Square KDS and TouchBistro conventions. Quantities in monospace so 1×, 2×, 3× align cleanly. Modifications ("no anchovy", "medium-rare", "VIP guest") appear as smaller, lighter text — they matter but aren't the primary read. Variations / seat numbers in footer line.

    ↳ Multilingual support deferred — see TouchBistro's KDS as reference when we add it.

  6. 6

    Footer meta bar — shift context, ticket counts by status

    KitchenManager reads this on every glance: avg prep time + count by status. Shift context (Dinner Service, 17:00–23:00) anchors time-of-day reasoning. Mirrors Toast's "manager log synced with Toast Web" idea but specific to KDS data only.

  7. 7

    Station filter pills + Manager view toggle

    Stations (Hot / Cold / Grill / Bar / Expo) map directly to website-spec.md §5.4 "Routing configurations assign tickets by prep station, menu category, or service type" — TouchBistro KDS pattern. Manager view toggle flips to a denser 6-column layout with re-assign / change-priority controls (answers spec §12 #6: "should KDS also have a non-full-screen mode for managers reviewing from the office?"). Counts on each pill (e.g. "All · 8", "Hot line · 3") borrowed from Square Dashboard filter chips.
